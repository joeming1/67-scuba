Split the work by ownership

Agree on the shared JSON contract first. Each engineer owns a separate seam so integration can happen early.

1

WorkBuddy + workflow backend

Owns the agent connection and safe ticket operations.

  • Prove WorkBuddy can call a local MCP tool first.
  • Build incident APIs, routing map, duplicate checks, and ticket state rules.
  • Expose tools for triage, work orders, sensor reads, and verified closure.
2

Student + technician interface

Owns the intake experience and the visible ticket journey.

  • Build free-text report form and ticket queue.
  • Show WorkBuddy's category, assignment, rationale, and timeline.
  • Add technician actions and a clear pending-triage state.
3

IoT + demo integration

Owns sensor evidence and a reliable live walkthrough.

  • Calibrate the LDR and send the agreed normalized payload.
  • Build sensor panel and same-payload simulator fallback.
  • Own demo reset, physical setup, and runbook.

24-hour build sequence

Get the WorkBuddy connection proven in hour one. Integrate each path as soon as it exists.

0–1 hour · prove the link

All: freeze the ticket contract and demo story.
Eng 1: WorkBuddy calls a stub MCP tool.
Eng 2: sketch queue from fixture data.
Eng 3: read LDR in light and dark.

1–4 hours · build in parallel

Eng 1: incident store, routing, MCP tools.
Eng 2: intake, queue, detail, timeline.
Eng 3: calibrate LDR and create simulator payload.

4–8 hours · first integration

Student reports and sensor events appear as pending incidents. WorkBuddy processes one and creates an assigned work order visible in the UI.

8–12 hours · close the loop

Add technician actions, duplicate protection, and sensor verification. Make a failed repair produce follow-up rather than closure.

12–16 hours · prove recovery

Show the failed reading, follow-up, brighter reading, and verified close. Keep the sensor simulator ready.

16–24 hours · freeze + rehearse

Stop adding features. Seed/reset the scenario, rehearse the pitch, and use the same reliable sequence each time.

The live demo: a repair that fails once

This shows why FixFlow follows the outcome instead of treating a notification or technician click as resolution.

Detect

Cover the LDR. A sustained dim reading creates a pending incident.

Ask WorkBuddy

WorkBuddy uses MCP to classify lighting and create the assigned work order.

Fail verification

Technician marks a repair attempt, but the sensor still reads dim.

Follow up

WorkBuddy records failed verification and leaves the case open.

Verify close

Raise the reading. WorkBuddy checks evidence and closes the ticket.

Keep the claim honestThe LDR creates an incident. A person prompts WorkBuddy to process it unless you have verified automatic agent triggering.
Fallback is part of the demoIf hardware or Wi-Fi fails, the simulator posts the same sensor JSON. Keep WorkBuddy live; don’t replace its tool calls with scripted agent text.
