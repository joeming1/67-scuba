DataLocal JSON store

Tickets, assignment responses, schedules, sensor evidence, and activity timeline.

TechnicianWhatsApp response page

Accept and schedule or decline from a phone; a decline messages the next available technician.

OutcomeVerified resolution

AI checks the completion photo; lighting tickets also require recovered sensor readings.

WhatsApp flow: Node.js API → Twilio WhatsApp → technician phone → mobile response page → Node.js API. Use a public HTTPS tunnel so the phone can reach the response page from any network.

24-hour sequence

Integrate early, freeze features with time left to rehearse.

0–1 hour

All: agree contract and story.
Eng 1: start API.
Eng 2: map screens.
Eng 3: check sensor range.

1–4 hours

Eng 1: routing, rules, persistence.
Eng 2: form, queue, actions.
Eng 3: simulator and LDR calibration.

4–8 hours

Student reports and three low readings create tickets visible in the same queue. Prevent duplicate sensor tickets.

8–12 hours

Finish technician schedule and decline flow; route declined assignments to the next available technician.

12–16 hours

Run the complete failure-then-recovery scenario with hardware and simulator fallback.

16–24 hours

Freeze features, reset data, polish the pitch, and rehearse the same demo repeatedly.

Demo: assignment to verified repair

Show the ticket moving through a simple technician response and repair process.

Detect

Simulate dim light or cover the LDR. Three readings create a ticket.

Notify

Open the assignment WhatsApp on the technician’s phone, using the public tunnel link.

Schedule or decline

Accept and choose a visit time, or decline to message the next available technician.

Attempt repair

Start work and mark the repair attempt while the room is still dim.

Follow up

Ticket stays open because the sensor still reports low brightness.

Verify close

Bright readings and an AI-approved completion photo confirm the repair.

Demo boundaries: assignments are fictional, student classification uses simple demo rules, and the sensor simulator is the fallback. WhatsApp needs Twilio settings; repair completion needs an OpenAI API key and photo evidence. No real UMHelpdesk integration is included.
